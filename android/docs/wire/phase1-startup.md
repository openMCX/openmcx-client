# Wire contract, phase 1: power-on to "ready"

What an on-network MCPTT and MCData client (3GPP Rel-19) sends and receives between power-on and "ready"
against OpenMCX. "Ready" means registered, service-authorised for MCPTT and MCData, and affiliated to the
provisioned groups, with the affiliation confirmed by a NOTIFY. The client is a native Android client.

Sources:
- Specifications: ETSI TS 124 379 V19.7.0, TS 124 282 V19.7.0 and TS 124 481 V19.3.0, cited by clause. TS 24.482 and
  TS 24.484 clauses are cited from the published specifications and not re-checked against a local copy; statements
  about them are marked *(verify)*.
- Server code: the MCPTT server (`server.cpp`), the MCData server (`data_server.cpp`) and the Go common services
  (IdMS, CMS and GMS) of openmcx-server. `src/` and `svc/` below name those directories. The file and line pointers
  were taken from an earlier layout of the server sources and may have moved; the behaviour described is what the
  servers did when the contract was written.
- SIP core: the Kamailio configuration of openmcx-server (`docker/kamailio.cfg`, cited below as `fx-kam`), which
  reaches RFC 5626 clients over their registered flow. Kamailio registrar and auth defaults were checked in the
  Kamailio 6.1.4 source.
- The HTTP examples in §1–§2 are real output. They were produced by running the IdMS, CMS and GMS handlers
  in-process against a lab fixture's `site.json` and signing key.
- The SIP examples come from the server code and from plaintext lab captures of the Kamailio-to-application-server leg.
  They show the server side verbatim; the client side is rewritten here to follow the specifications.

## 0. Start-up order (what OpenMCX actually requires)

```
 1  HTTPS  GET  idms  /.well-known/openid-configuration
 2  HTTPS  GET  idms  /authorize?...            -> JSON {request_id}
 3  HTTPS  POST idms  /login                    -> 302 Location: redirect_uri?code&state
 4  HTTPS  POST idms  /token                    -> access_token, id_token (no refresh_token)
 5  HTTPS  GET  idms  /jwks                     -> verify id_token (RS256)
 6  HTTPS  GET  proxy /cms/xcap-root/3gpp.mcptt.user-profile/users/<MCPTT-ID>/index
 7  HTTPS  GET  proxy /gms/xcap-root/org.openmobilealliance.groups/global/byGroupID/<group>   (per group)
 8  TLS (mutual) to sip-core:5061; REGISTER -> 401 -> REGISTER+Authorization -> 200
 9  PUBLISH poc-settings  -> sip:mcptt@   (407, retry) -> 200 + SIP-ETag           MCPTT authorised
10  SUBSCRIBE presence    -> sip:mcptt@   -> 200 (Expires: 3600) ; NOTIFY (empty status)
11  PUBLISH presence      -> sip:mcptt@   -> 200 + SIP-ETag ; NOTIFY status="affiliated"   MCPTT ready
12  PUBLISH poc-settings  -> sip:mcdata@  -> 200 + SIP-ETag                          MCData authorised
13  SUBSCRIBE presence    -> sip:mcdata@  -> 200 (Expires: 4294967295) ; NOTIFY (current/implicit groups)
14  PUBLISH presence      -> sip:mcdata@  -> 200 + SIP-ETag ; NOTIFY status="affiliated", echoed p-id   MCData ready
```

Hard ordering constraints enforced by the servers:
- Step 9 must precede 10 and 11. Without service authorisation, `authenticated()` throws and the MCPTT server answers
  **403** (`src/server.cpp:1153-1167`, `:4190-4195`).
- **Step 10's 200 must arrive before step 11 is sent.** The MCPTT server refuses an affiliation PUBLISH with 403
  unless an unexpired presence subscription exists (`src/server.cpp:3797-3800`). The spec only recommends this order
  (TS 24.379 §9.2.1.1); OpenMCX makes it mandatory.
- Step 12 must precede 13 and 14. Otherwise the MCData server answers 404 with warning 141, or 403
  (`src/data_server.cpp:3990-4013`).
- MCPTT and MCData are independent after step 8 and may run in parallel. Steps 6 and 7 are needed only for the
  profile and group data; the SIP servers do not check that the client fetched them.

## 1. IdMS / OIDC (TS 24.482 as implemented)

Clauses: TS 24.482 §6 user authentication, Annex A HTTP profile *(verify)*. TS 24.379 §7.1 and
TS 24.282 §7.1 require an access token before service authorisation.

Implementation: `svc/idms.go:22-29` (routes). The IdMS listens on `https://idms:8443` with TLS 1.2 or later, server
certificate only (`services/cmd/mcx-common/main.go:64,92-99`). It is not behind http-proxy.

### 1.1 Discovery: `GET https://idms:8443/.well-known/openid-configuration` (`svc/idms.go:31-37`)
```
HTTP 200  Content-Type: application/json  Cache-Control: no-store
{"authorization_endpoint":"https://idms:8443/authorize","code_challenge_methods_supported":["S256"],
 "id_token_signing_alg_values_supported":["RS256"],"issuer":"https://idms:8443","jwks_uri":"https://idms:8443/jwks",
 "response_types_supported":["code"],"scopes_supported":["openid","3gpp:mc:ptt_service","3gpp:mc:data_service",
 "3gpp:mc:ptt_key_management_service"],"subject_types_supported":["public"],"token_endpoint":"https://idms:8443/token"}
```
There is no `refresh_token` grant, no `userinfo_endpoint` and no `end_session_endpoint`.

### 1.2 Authorization request: `GET /authorize?…` (`svc/idms.go:61-83`)

| Param | Required by server | Value |
|---|---|---|
| `response_type` | = `code` | `code` |
| `client_id` | = `oauth_client_id` | `mcx-lab-client` |
| `redirect_uri` | exact match in `oauth_redirect_uris` | `http://127.0.0.1:8900/callback` |
| `scope` | must contain the word `openid`; nothing else is checked | `openid 3gpp:mc:ptt_service 3gpp:mc:data_service` (add `3gpp:mc:ptt_key_management_service` only for protected groups) |
| `state` | non-empty, ≤1024 | random |
| `nonce` | non-empty, ≤1024 (**mandatory**, stricter than OIDC for code flow) | random |
| `code_challenge` | exactly 43 base64url chars | `BASE64URL(SHA256(verifier))` |
| `code_challenge_method` | = `S256` (**mandatory**) | `S256` |

**Deviation:** the response is JSON, not an HTML login page or a redirect:
```
HTTP 200  Content-Type: application/json
{"request_id":"9Zkb5IwWC-adZAKuEFn0gGIrjzlFHvCo1rKoLHQFQ04"}
```
Errors: 400 `{"error":"invalid_request"}`; 429 `temporarily_unavailable`. The `request_id` is valid for 5 min.

### 1.3 Non-interactive login: `POST /login` (`svc/idms.go:85-125`)
```
POST /login HTTP/1.1
Host: idms:8443
Content-Type: application/x-www-form-urlencoded

request_id=9Zkb5IwWC-adZAKuEFn0gGIrjzlFHvCo1rKoLHQFQ04&username=alice&password=<password>
```
```
HTTP 302
Location: http://127.0.0.1:8900/callback?code=S_D4NB6xs5PVg-u88q1vGQXW9YEg8CimuclNKmptmwQ&state=st123
```
- **Do not follow the redirect.** Read `code` and `state` from `Location` and check `state`. Nothing listens on
  127.0.0.1:8900.
- Bad credentials give 401 `{"error":"access_denied"}`. **The `request_id` is consumed even on failure**, so restart
  from `/authorize`.
- The code is valid for **60 s** and is single-use.

### 1.4 Token request: `POST /token` (`svc/idms.go:127-167`)

This is a public client with no client authentication.
```
POST /token HTTP/1.1
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&client_id=mcx-lab-client&redirect_uri=http%3A%2F%2F127.0.0.1%3A8900%2Fcallback&code=…&code_verifier=<43..128 chars [A-Za-z0-9-._~]>
```
```
HTTP 200  Content-Type: application/json  Cache-Control: no-store
{"access_token":"eyJ…","expires_in":3600,"id_token":"eyJ…","token_type":"Bearer"}
```
Any mismatch gives 400 `{"error":"invalid_grant"}`. **There is no `refresh_token` and no `scope` in the response.**

### 1.5 Tokens (`svc/jwt.go:16-31,46-59,119-123`)

Both tokens are JWS compact, header `{"alg":"RS256","kid":"<b64url(sha256(n))[0:12 bytes]>","typ":"JWT"}`, signed with
the same key.

| Claim | ID token | Access token |
|---|---|---|
| `iss` | `https://idms:8443` | same |
| `aud` (string) | `mcx-lab-client` | `mcx-lab-server` |
| `sub` | MCPTT ID | MCPTT ID |
| `exp`/`iat` | iat + `token_ttl_seconds` (3600) | same |
| `jti` | random | random |
| `nonce` | from the authorize request | — |
| `mc_id`, `mcptt_id`, `mcdata_id`, `sip_uri`, `client_id` | yes | yes |
| `token_type` | `id` | `access` |
| `scope` | — | the requested scope string, echoed |

Real decoded access token for alice:
```json
{"iss":"https://idms:8443","sub":"sip:alice.mcptt@mcx.test","aud":"mcx-lab-server","exp":1790340026,"iat":1790336426,
 "jti":"…","mc_id":"sip:alice.mc@mcx.test","mcptt_id":"sip:alice.mcptt@mcx.test","mcdata_id":"sip:alice.mcdata@mcx.test",
 "sip_uri":"sip:alice@mcx.test","client_id":"urn:uuid:8034b521-39ae-47bd-b7bf-aaa7a6a316ef","token_type":"access",
 "scope":"openid 3gpp:mc:ptt_service 3gpp:mc:data_service"}
```
JWKS (`GET /jwks`, `svc/idms.go:40-42`) returns `{"keys":[{"alg":"RS256","e":"AQAB","kid":"…","kty":"RSA","n":"…","use":"sig"}]}`.

What the client must do with the tokens:
- Verify the ID token: signature by `kid`, `iss`, `aud == client_id`, `nonce`, and `exp`/`iat` with skew allowed.
- Check `mcptt_id`, `mcdata_id`, `sip_uri` and `client_id` against provisioning. **The MC client ID in every
  mcptt-info and mcdata-info body must equal the `client_id` claim**, which the IdMS provisions per user
  (`site.json users[].client_id`). The client must not generate it.
- Treat the access token as opaque. It is used as `Authorization: Bearer` over HTTP (§2) and inside
  `<mcptt-access-token>`/`<mcdata-access-token>` over SIP (§4). The servers validate it by introspection
  (`POST /introspect`, Basic auth as `mcx-lab-server`, `svc/idms.go:169-186`), which the client never calls.

### 1.6 Lifetimes and refresh

| Item | Lifetime | Source |
|---|---|---|
| `request_id` | 5 min | `svc/idms.go:80` |
| code | 60 s | `svc/idms.go:117` |
| access/ID token | `token_ttl_seconds` = 3600 s | `site.json`, `svc/jwt.go:122` |
| server iat skew | +60 s | `svc/jwt.go:95` |

**There is no refresh.** Renewing a token means repeating steps 2–4 (authorize, login, token) and then
re-authorising both services (§4.5). This must happen before `exp`. When the token expires, the MCPTT and MCData
servers drop the user's authorisation and affiliations **silently**: no NOTIFY and no SIP signal
(`src/server.cpp:4688-4700`; `src/data_server.cpp:310`).

## 2. CMS and GMS over the HTTP proxy (TS 24.481, TS 24.484)

Clauses: TS 24.481 §6.2.2–6.2.3 (the GMC uses TLS per TS 24.482 Annex A), §6.3.3 (retrieval, RFC 4825 "Fetch a
Document"), §7.2.10.2 (`byGroupID`) and §7.2.12 (authorisation policy). TS 24.484 covers the user profile
*(not checked against a local copy)*.

Transport (`services/cmd/mcx-http-proxy/main.go:75,92-96`):
- HTTPS with TLS 1.2 or later to `http-proxy:8443`. Server certificate SAN `http-proxy`.
- **No client certificate.** The public listener does not ask for one.

Authentication:
- `Authorization: Bearer <access_token>` (`svc/documents.go:174-192`).
- `X-3GPP-Intended-Identity` is **ignored**. The identity comes from the token's `mcptt_id`.
- A missing or invalid token gives `401` with `WWW-Authenticate: Bearer realm="mcx-common"` and body
  `{"error":"invalid_token"}`.

Proxy rules (`services/cmd/mcx-http-proxy/main.go:134-191`):
- Only `/cms/xcap-root/…`, `/gms/xcap-root/…`, `/lms/location/…`, `/kms/…` and `/content/mcdata/files…` are
  forwarded, with the first segment stripped. Anything else gives 404.
- The path must equal its `path.Clean` form: no trailing `/`, no `//` and no `..`. Otherwise the proxy answers 400.
- Request bodies are limited to 1 MiB.
- If the upstream is down the proxy answers 502 `upstream unavailable`.
- Percent-encoding in the path is fine; `sip%3A…%40…` and a raw `sip:…@…` both work.

### 2.3 Group or profile change notification

TS 24.481 §6.3.13 defines `SUBSCRIBE xcap-diff` to the GMS subscription-proxy PSI. **This is not available.**
- Kamailio routes client requests only to `sip:mcptt@` and `sip:mcdata@` (`fx-kam:158-175`).
- The MCPTT server accepts `xcap-diff` only for group-key (GKTP) documents, only when keying is configured, and
  only with an access token and client ID. In this lab it answers 403 (`src/server.cpp:3682-3697`).
- `SUBSCRIBE poc-settings` (TS 24.379 §7.3.6) is not supported by the MCPTT server, which answers 489
  (`src/server.cpp:3741-3744`).

Instead, re-GET the documents with `If-None-Match` after each token renewal and on app foreground. The servers
return 304 when nothing changed (`svc/documents.go:285-297`).

## 3. SIP registration through Kamailio

Clauses:
- TS 24.379 §7.2.1 and §7.2.1AA (Contact feature tags), and §7.1 (one shared registration for all MC services).
- TS 24.282 §7.2.1 and §7.2.1AA.
- RFC 3261 §10, RFC 5626 and RFC 5627 (none of their extensions is implemented, see below).

### 3.1 Transport (`fx-kam:69`, `tls.cfg`)
- **Mutual TLS is required.** Kamailio has `require_certificate = yes` and `verify_certificate = yes`, TLS 1.2 or
  later. Any request not over TLS, or without a verified peer certificate, gets `403 TLS required`.
- The client presents `client-a.crt`. Kamailio checks only the chain to the lab CA; the CN is not compared to
  the AoR.
- The client verifies `sip-core.crt`: SAN `sip-core`, ECDSA key.
- Connect to `sip-core:5061` with SNI `sip-core`. `--debug-sip` labs use plain TCP on 5060 instead.
- Keep one TLS flow for all SIP. Responses and every request towards the client come back on it (§3.4).

### 3.2 Digest authentication (`fx-kam:116-127`; Kamailio `auth` 6.1.4 defaults)

| Item | Value |
|---|---|
| Realm | `mcx.test` |
| Algorithm | MD5. The challenge has **no `algorithm` param and no `qop`** (`auth_challenge("mcx.test","0")`). Use RFC 2069-style `response=MD5(HA1:nonce:HA2)` with no `nc`/`cnonce`. |
| HA1 | `MD5("alice:mcx.test:" + sip_password)`; the server computes HA1 from the plaintext (`calculate_ha1=1`) |
| REGISTER | `401` + `WWW-Authenticate` → `Authorization` |
| Every other request | `407` + `Proxy-Authenticate` → `Proxy-Authorization`. This includes **in-dialog** requests (re-SUBSCRIBE, BYE, UPDATE…). Only ACK and CANCEL are exempt. |
| Nonce lifetime | 300 s. It is reusable within that time (no nc or one-time nonce), so the client may send credentials pre-emptively with the cached nonce. After it expires, expect a new challenge (`stale=true`) and retry transparently. |
| Identity binding | `From` user must equal the digest username and `From` host must be `mcx.test`, else `403 Identity mismatch`. For REGISTER the same applies to `To`. |
| Asserted identity | Kamailio strips any client `P-Asserted-Identity` or `P-Preferred-Identity` and inserts `P-Asserted-Identity: <sip:alice@mcx.test>` |

**From must be exactly `<sip:alice@mcx.test>`: no URI parameters and no user=phone.** The MCPTT and MCData
servers compare the printed From URI with the PAI string (`src/server.cpp:3601-3603`, `src/data_server.cpp:713`,
`src/sip.cpp:510`). A display name is allowed.

### 3.3 REGISTER (`fx-kam:51,113-123`; Kamailio registrar defaults)

Registrar behaviour:

| Item | Behaviour |
|---|---|
| `max_expires` | 3600 |
| `min_expires` | 60 |
| default expiry | 3600 |
| Request-URI | not checked; use `sip:mcx.test` |
| Bindings | stored in memory only (`db_mode 0`) and **lost if Kamailio restarts**. After a flow failure or a 403 or 480 path, re-register. |
| Body | ignored. **REGISTER-based service authorisation (TS 24.379 §7.2.1 with an mcptt-info body) is not supported**: there is no third-party REGISTER. Use §4. |
| `outbound_mode` = 0 (none) | `Supported: outbound` is ignored: the 200 has no `Require: outbound` and no `Flow-Timer`. **`Require: outbound` is answered `420 Bad Extension`**, so do not send it. |
| `reg-id` + `+sip.instance` | Both are stored. A later REGISTER with the same instance and reg-id **replaces** the binding, and a new Call-ID for the same instance deletes the older bindings (registrar `save.c:350-368,800-826`). Always register with a stable `+sip.instance` and `reg-id=1`. |
| Flow reuse | `fix_nated_register()` stores the flow source (ip:port;transport) as `received` (`fx-kam:53-54,121`), so later requests to the client use the flow |

- Kamailio's registrar supports GRUU: do **not** send `Supported: gruu` (unneeded).
- Kamailio's 200 lists every binding of the AoR. Find your own binding by `+sip.instance` and `reg-id` and read its

### 3.4 Flow reuse: requirements the client must meet

These come from the SIP core configuration, `fx-kam:121,126,171-172,195,231-235`.
- **The Contact host:port must differ from the flow's source address.** Use a `<random>.invalid` host, as in the
  example. Kamailio's `add_contact_alias()` adds `;alias=ip~port~tls` to the Contact of every client request and
  2xx *only if* the Contact differs from the source. The alias is what routes in-dialog requests such as NOTIFY and
  BYE back over the flow (`handle_ruri_alias` + `set_forward_no_connect`). An IP:port Contact that matches the
  source gets no alias, and in-dialog requests then fall back to Contact-based routing.
- Kamailio **never dials the client** (`set_forward_no_connect`). If the flow is down, requests to the client fail
  (480 or 477). Re-register on a new flow; the same instance and reg-id replace the binding.
- Keepalive: send CRLFCRLF on the TLS flow. Kamailio answers with CRLF (`tcp_crlf_ping=1` is the core default).
  There is no `Flow-Timer`, so the client chooses the interval (RFC 5626 suggests 95–120 s).
- Idle connection lifetime is `tcp_connection_lifetime=3605` s (`fx-kam:55`).
- Requests from the client must use this same flow: responses on it, and ACK/CANCEL matched to the peer by `$si`
  (`fx-kam` INVITE peer binding).
- Initial requests need no preloaded `Route`. Kamailio routes on the Request-URI. If `Route: <sip:sip-core:5061;transport=tls;lr>`
  is included, it is not consumed for initial requests and simply passes through to the AS, which is harmless.
- **Only PSIs are routable.** Out of dialog, a client may target only `sip:mcptt@mcx.test` and `sip:mcdata@mcx.test`.
  Everything else gets `403 Route forbidden` (`fx-kam:158-175`). That includes `SUBSCRIBE reg` to your own AoR and
  OPTIONS pings to the domain, so do not send them.
- Kamailio record-routes only INVITE and SUBSCRIBE (`fx-kam:151`). The Record-Route is
  `<sip:sip-core;transport=tls;lr=on;ftag=…>`; use it as the dialog route set.

## 4. Service authorisation (PUBLISH `poc-settings`)

OpenMCX uses only the PUBLISH method (TS 24.379 §7.2.2 and TS 24.282 §7.2.2). The access token travels in the
PUBLISH body; there is no third-party REGISTER.

### 4.1 Common headers (TS 24.379 §7.2.1A, TS 24.282 §7.2.1A)

| Header | MCPTT | MCData | Server checks? |
|---|---|---|---|
| Request-URI | `sip:mcptt@mcx.test` | `sip:mcdata@mcx.test` | Kamailio routes on it |
| `P-Preferred-Service` | `urn:urn-7:3gpp-service.ims.icsi.mcptt` | `urn:urn-7:3gpp-service.ims.icsi.mcdata` | no (send anyway) |
| `Event` | `poc-settings` | `poc-settings` | yes |
| `Expires` | `4294967295` | `4294967295`; `0` logs off | MCPTT: ignored. MCData: `0` means log-off (`src/data_server.cpp:714-727`) |
| `SIP-If-Match` | the previous `SIP-ETag` when refreshing | same | yes (§4.5) |
| `Content-Type` | `multipart/mixed;boundary=…` | same | parsed strictly (§7) |

### 4.2 MCPTT body (TS 24.379 §7.2.2 steps 5–6, Annex F.1, §7.4.1.2.2)

The MCPTT server needs a part `application/vnd.3gpp.mcptt-info+xml` containing both `<mcptt-access-token>` and
`<mcptt-client-id>` (`src/server.cpp:3598-3667`).
- It does **not** require the `application/poc-settings+xml` part, and it ignores the part's contents: answer mode,
  profile index and multiplex are not used. This deviates from §7.3.3, which requires that part. Send it anyway
  as the spec says.
- An `application/mikey` part is used only when keying is configured (§7.2.2 step 3); omit it in phase 1.

Notes on the body:
- The `<answer-mode>` values are `automatic` and `manual`, per RFC 4354. The prose of §7.2.2 step 6a says

| Check | On failure |
|---|---|
| PAI present and equal to the From URI | 403 |
| token and client ID present | 403 |
| Introspection: `active`, `sip_uri == PAI`, `client_id == <mcptt-client-id>` | 403 |
| `sub == mcptt_id` | 403 |
| The same SIP identity is already bound to a different MCPTT ID or client ID ("live remapping refused") | 403 |
| The MCPTT ID is already bound to another SIP identity | 403 |

### 4.4 Settings-only PUBLISH (TS 24.379 §7.2.3, TS 24.282 §7.2.3)

TS 24.379 §7.2.3 describes a PUBLISH with `<mcptt-request-uri>` and client ID but no token. The MCPTT server
**treats every `poc-settings` PUBLISH as service authorisation**, so one without a token gets 403. Always include
the token.

### 4.5 Token renewal and re-authorisation

The token expires 3600 s after issue. Re-login (§1) and re-PUBLISH `poc-settings` to both PSIs **before** `exp`,
for example at `exp − 300 s`. Send `SIP-If-Match: <last SIP-ETag>` with the new token.

| Case | MCPTT server | MCData server |
|---|---|---|
| With a matching `SIP-If-Match` | keeps subscription and affiliations, updates the expiry, returns a new ETag | same |
| **Without `SIP-If-Match`**, user already known | **creates a fresh user record**: drops the subscription and affiliations and releases calls (`src/server.cpp:3641-3648`). No NOTIFY is sent, so the client must SUBSCRIBE and affiliate again. | keeps state, unless the MCData ID or client ID changed |
| Stale `SIP-If-Match` (for example after a server restart) | 412. Retry without `SIP-If-Match`, then redo §5. | 412. Retry without it. |
| `Expires: 0` | not a log-off; handled as a normal authorisation | log-off |

There is no MCPTT log-off. To leave the service, stop refreshing and de-register; state ends at token expiry.

For MCData the changes are:
- the PSI, the ICSI and the mcdata-info part, with `<mcdata-request-uri>` = own MCData ID and `<mcdata-client-id>`;
- the PIDF namespace `urn:3gpp:ns:mcdataPresInfo:1.0` and entity = MCData ID.

Rules for the PIDF body (TS 24.379 §9.2.1.2 step 5, §9.3.1.2; TS 24.282 §8.2.2, §8.4.1.2):
- There is exactly one `<tuple>`, with `id` = MC client ID.
- There is one `<affiliation group=…>` per group of interest, **without `status` and `expires`**.
- `<p-id>` is globally unique and sits in the MC namespace, as a child of `<presence>`.
- The PUBLISH carries the **full state**. Both servers *replace* the group set with the one in the PIDF, so any
  group left out is de-affiliated. For MCData, include the implicit affiliations learned from the first NOTIFY.

Server requirements beyond the spec:

| Requirement | MCPTT (`src/server.cpp:3770-3822`) | MCData (`src/data_server.cpp:761-812`) |
|---|---|---|
| Active presence subscription first | **required**, else 403 | not required |
| `<mcptt-client-id>` in mcptt-info | **required**, must equal the bound client. The spec asks only for `<mcptt-request-uri>`. | not required |
| `<…-request-uri>` = own ID | required | required |
| PIDF entity and tuple id = own ID and client | required | required, and the MCData namespace is mandatory |
| Each group | the MCPTT ID must be in the group's members. Beyond N2 (`MaxAffiliationsN2`), extra groups are dropped silently; only the NOTIFY shows it. | the MCData ID must be in the group's `mcdata.members` |
| `SIP-If-Match` | **mandatory once a publication exists**: omitting it gives 412, which deviates from RFC 3903 §6 | only checked if present |
| De-affiliate all (`Expires: 0`) | **PIDF still required** (it contradicts NOTE 2), and mcptt-info is required | PIDF optional; mcdata-info required |
| Failure codes | 403 (no Warning), 412 | 403, 412 |
| 200 | `Expires: 4294967295` + `SIP-ETag` (`Expires: 0` without an ETag when removing) | same |

Affiliation is immediate. Neither server models the "affiliating" state.

### 5.3 NOTIFY and how "affiliated" is confirmed

Real MCPTT NOTIFY, captured on the Kamailio leg:
```
NOTIFY sip:alice@client-a:5060;transport=tcp SIP/2.0
From: <sip:mcptt@mcx.test>;tag=ec2a30b4-…
To: <sip:alice@mcx.test>;tag=d153a762-…
Contact: <sip:mcptt@mcx-server:5060;transport=tcp>;+g.3gpp.mcptt;+g.3gpp.icsi-ref="urn%3Aurn-7%3A3gpp-service.ims.icsi.mcptt"
Event: presence
Subscription-State: active;expires=3600
Content-Type: application/pidf+xml

<?xml version="1.0"?><presence xmlns="urn:ietf:params:xml:ns:pidf" xmlns:mc="urn:3gpp:ns:mcpttPresInfo:1.0" entity="sip:alice.mcptt@mcx.test"><tuple id="urn:uuid:2e921576-…"><status><mc:affiliation group="sip:operations-chat@mcx.test" status="affiliated"/></status></tuple><mc:p-id>9drXEPAQozmKWOe5X1OPhHUMpPPTZ4tS-2rWrXZg_-I</mc:p-id></presence>
```
Real MCData NOTIFY, the first one after SUBSCRIBE, when nothing is affiliated yet:
```
Event: presence
Subscription-State: active
Content-Type: application/pidf+xml

<?xml version="1.0"?><presence xmlns="urn:ietf:params:xml:ns:pidf" xmlns:mc="urn:3gpp:ns:mcdataPresInfo:1.0" entity="sip:alice.mcdata@mcx.test"><tuple id="urn:uuid:ad4a4613-…"><status></status></tuple></presence>
```
- The client receives the Request-URI as its Contact without `;alias`, which Kamailio strips. The NOTIFY carries
  `P-Asserted-Identity: <sip:mcptt@mcx.test>` or `<sip:mcdata@mcx.test>`, inserted by Kamailio for the AS
  (`fx-kam:131-132`). Verify it. Answer `200 OK` with no body.
- **The client is affiliated to G when the latest NOTIFY has `<affiliation group="G" status="affiliated"/>` under
  the tuple whose `id` is its client ID.** Treat any group that is absent as not affiliated. There is no `expires`
  attribute.
- MCPTT: `<p-id>` is a **fresh random value, not the PUBLISH's p-id**, which deviates from §9.2.1.3 and §9.2.2.3.5.
  Correlate by group set. The body is always the full state, and an empty `<status/>` means nothing is affiliated.
- MCData: `<p-id>` **echoes** the p-id of the PUBLISH that caused the NOTIFY, and is omitted when the NOTIFY was
  not caused by a PUBLISH (`src/data_server.cpp:813-823`).
- `Subscription-State: terminated;reason=noresource` (MCData) means log-off or de-subscription. Subscribe again
  after re-authorising.

## 6. Refresh behaviour

| Item | Interval / trigger | How | Server truth |
|---|---|---|---|
| REGISTER | granted expiry ≤ 3600 s; refresh at about 50–80 % (e.g. 3600 → 2400 s) | same Call-ID, CSeq+1, same instance and reg-id, on the same flow | `max_expires 3600` (`fx-kam:51`) |
| New flow after connection loss | immediately | REGISTER from a new connection with the same instance and reg-id (replaces the binding). Then re-send in-dialog SUBSCRIBE refreshes, because NOTIFY routes via the old alias until the next client request in that dialog. The simplest option is new SUBSCRIBEs. | registrar `save.c:800-826` |
| CRLF keepalive | client-chosen, e.g. 90–120 s | `\r\n\r\n` → expect `\r\n` | `tcp_crlf_ping` default |
| Access token | at `exp − ~300 s` (TTL 3600) | full re-login (§1.2–1.4), then §4.5 re-PUBLISH to both PSIs with `SIP-If-Match` | no refresh_token (`svc/idms.go:166`) |
| MCPTT `poc-settings` publication | no RFC 3903 expiry (4294967295) | only on token renewal | `src/server.cpp:3668-3669` |
| MCData `poc-settings` publication | same | same | `src/data_server.cpp:756` |
| MCPTT presence subscription | **3600 s**, server-imposed | in-dialog SUBSCRIBE with `Expires: 4294967295` and `Accept: application/pidf+xml` before 3600 s, e.g. at 3000 s. On expiry the server clears all MCPTT affiliations silently (`src/server.cpp:4677-4685`). | `src/server.cpp:3760-3762` |
| MCData presence subscription | 4294967295 (no refresh needed) | re-subscribe after a flow change or re-auth | `src/data_server.cpp:858-861` |
| Affiliation publications (both) | 4294967295 | re-PUBLISH only on change or after reset, full state, with `SIP-If-Match` | as §5.2 |
| Group or profile documents | no notification | GET with `If-None-Match` after token renewal or on foreground | §2.3 |
| Digest nonce | 300 s | cache it and retry on 401/407 | Kamailio default |
| Session timers | n/a in phase 1 (INVITE only) | — | — |

## 7. Encoding rules the servers enforce

Multipart parser (`src/protocol.cpp:848-915`, `src/sip.cpp:516-535`):
- The body is at most 64 KiB, with at most 8 parts. The type is `multipart/mixed` or `multipart/related`.
- **No preamble.** The body must start with `--boundary` followed by CRLF; a leading CRLF is tolerated.
- Part headers end with CRLFCRLF and must include `Content-Type`. Parameters are stripped and the value is
  compared in lower case.
- Each part ends with `CRLF--boundary`. The closing `--boundary--` may be followed only by whitespace.

XML (`src/protocol.cpp:50-62,80-109`, `src/mcdata.cpp:29-68`):
- DTDs and entities are rejected, and at most one of each element is allowed.
- A `contentType` element has exactly one wrapper child. For MCPTT that is `mcpttURI` or `mcpttString` (plus
  `mcpttBoolean` for booleans); for MCData it is `mcdataURI`, `mcdataString` or `mcdataBoolean`.
- `type` is absent or `Normal`. `Encrypted` is rejected.
- Emit elements in Annex F.1 and D.1 schema order:
  - mcptt-Params: `mcptt-access-token`, `session-type`, `mcptt-request-uri`, …, `mcptt-client-id`, …
  - mcdata-Params: `mcdata-access-token`, `request-type`, `mcdata-request-uri`, …, `mcdata-client-id`, …

## 9. Deviations and risks (summary)

| # | Issue | Impact on the Android client |
|---|---|---|
| 1 | `/authorize` returns JSON `{request_id}` and login is a proprietary `POST /login`. There is no browser page. | **An AppAuth Custom Tab flow cannot work against this IdMS.** Implement the direct HTTP flow as the lab login and keep AppAuth for a real IdMS. The redirect URI is fixed to `http://127.0.0.1:8900/callback`, so never follow it. |
| 2 | No refresh token; TTL 3600 s | Re-login every hour with stored credentials, then re-authorise both services. If this is missed, the servers de-authorise silently. |
| 3 | The MC client ID is provisioned and bound in the token | Use `client_id` from provisioning or the token for `+sip.instance`, the tuple id, `<…-client-id>` and the `<entity id>`. A different value gives 403. |
| 4 | Mutual TLS is required at the SIP core | The Keystore must hold the client certificate and key (RSA, PKCS#8). Lab certificates last 30 days. |
| 5 | Every client request is digest-challenged (407), including in-dialog ones. No qop, MD5. | The UA must handle 407 on in-dialog requests and cache the nonce. |
| 6 | `Require: outbound` → 420; no `Require: outbound` or `Flow-Timer` in the 200 | Send only `Supported: outbound`. Do not treat the missing `Require: outbound` as "no flow". The SIP core reuses the flow anyway. |
| 7 | Alias routing works only if the Contact differs from the source address | Use a `.invalid` Contact host. |
| 8 | No REGISTER-based service authorisation and no third-party REGISTER | Always use PUBLISH `poc-settings` (§4). |
| 9 | MCPTT re-authorisation without `SIP-If-Match` wipes the subscription and affiliations silently | Always send `SIP-If-Match`. On 412, re-authorise fresh and redo SUBSCRIBE and PUBLISH. |
| 10 | MCPTT affiliation PUBLISH needs the subscription first, `<mcptt-client-id>` in mcptt-info, `SIP-If-Match` after the first publication, and a PIDF even with `Expires: 0` | Follow the §5.2 table exactly. |
| 11 | The MCPTT presence subscription is forced to 3600 s and un-subscribing de-affiliates | Refresh in-dialog before 3600 s. Never send `Expires: 0` unless you mean to leave all groups. |
| 12 | The MCPTT NOTIFY `p-id` is random; MCData echoes it | Confirm by group set, not by p-id, at least for MCPTT. |
| 13 | The GMS shows only self in `<list>` and an empty MCData member list; there is no xcap-diff | The group UI cannot list members. Poll with ETag. |
| 14 | The CMS profile AUID is proprietary (the schema and MIME type follow TS 24.484); there are no MCData, service or UE config documents | Read the rights as boolean `<cp:actions>` elements. Take MCData settings and targets from provisioning. |
| 15 | MCPTT failures give 403 with no Warning; MCData exceptions give 400 | Error mapping cannot rely on Warning codes. |
| 16 | Kamailio bindings are memory-only and only PSIs are routable | Re-register on 480 or after a flow loss. Do not send SUBSCRIBE reg or OPTIONS. |
| 17 | The From URI must be exactly `sip:<user>@mcx.test` | No URI parameters in From. |
| 18 | The multipart parser is strict (no preamble, ≤ 8 parts, ≤ 64 KiB) | Generate canonical multipart. |
